# 0008 — IRON 1.4 migration: the `Runtime` callback pattern

- **Date** 2026-08-20
- **Context** `C:\dev\mlir-aie` was upgraded tonight from a pinned mlir-aie
  1.3.4 checkout to `main` (commit `7e00b57955e`, past the v1.4.1 release), via
  `python utils\iron_setup.py --dev`. `aie/iron/` was substantially rewritten
  upstream, not just one function's signature. This note captures the concrete
  before/after code patterns needed to port our `experiments/`/`tools/` design
  scripts. See [`tasks/0058`](../../tasks/0058-m11-iron-1.4-migration/TASK.md)
  for which files were actually migrated and verified.

## The core change: `Runtime` sequence body is now a callback, not a context manager

**Old (1.3.4):**

```python
rt = Runtime()
with rt.sequence(in_ty, out_ty) as (X, Y):
    rt.start(worker)
    tg = rt.task_group()
    rt.fill(fifo_in.prod(), X, tap=tap, task_group=tg)
    rt.drain(fifo_out.cons(), Y, tap=tap, wait=True, task_group=tg)
    rt.finish_task_group(tg)
return Program(dev, rt).resolve_program()
```

**New (1.4.x):**

```python
def sequence(X, Y, fin_prod, fout_cons):
    tg = TaskGroup()
    fin_prod.fill(X, tap=tap, group=tg)
    fout_cons.drain(Y, tap=tap, wait=True, group=tg)
    tg.finish()

rt = Runtime(sequence, [in_ty, out_ty, fifo_in.prod(), fifo_out.cons()])
return Program(dev, rt, workers=[worker]).resolve_program()
```

Concrete transformation rules, in order:

1. **`Runtime()` takes no more zero-arg construction.** It is now
   `Runtime(seq_fn, fn_args=None, *, strict_task_groups=True)`, mirroring
   `Worker(core_fn, fn_args)`. `seq_fn` is a plain Python function; it is
   called once, eagerly, at MLIR-resolve time (inside `Program.resolve_program`),
   the same way `Worker.core_fn` already ran.

2. **The `with rt.sequence(...) as (...):` block is gone.** What used to be
   the tuple of runtime buffer types passed to `.sequence(...)` is now the
   **type entries of `fn_args`**, in the same order — a `np.ndarray[...]`
   type or a scalar type (e.g. `np.int32`) declares a runtime input and is
   replaced with a live SSA-backed argument (`RuntimeData` for a tensor type,
   a bare SSA value for a scalar). A concrete **int** in `fn_args` instead
   folds to an `arith.constant` (useful for a static loop bound shared with
   the dynamic EmitC path — see `Runtime.__init__`'s docstring). Anything
   else in `fn_args` (an `ObjectFifoHandle`, a `Buffer`, a `Kernel`, a
   `ScratchpadParameter`, a `WorkerRuntimeBarrier`, ...) passes through to
   the body unchanged, exactly like `Worker.fn_args` already worked.

3. **`rt.start(worker)` is REMOVED entirely.** Workers are no longer started
   from inside the sequence body. They are now passed directly to `Program`:
   `Program(device, rt, workers=[worker, ...])`. If a design has multiple
   workers, pass the whole list here — there is no per-worker `.start()` call
   anywhere any more.

4. **`rt.fill(fifo.prod(), buf, ...)` / `rt.drain(fifo.cons(), buf, ...)`
   become methods ON the fifo endpoint handle itself**, with the runtime
   buffer as the first positional arg (source for `fill`, dest for `drain`):
   `fifo.prod().fill(buf, ...)` / `fifo.cons().drain(buf, ...)`. All the old
   keyword args survive unchanged EXCEPT one rename:
   **`task_group=` is now `group=`.** (`tap=`, `wait=`, `packet=`,
   `offset_parameter=`, `sizes=`, `strides=`, `offset=`, `transfer_len=`,
   `managed=` are all still there, same names — see
   `aie/iron/dataflow/objectfifo.py::ObjectFifoHandle.fill/.drain`.)
   In practice you usually want the *handle* object available inside the
   body — either close over the `fifo.prod()`/`fifo.cons()` value from the
   enclosing scope, or (more consistent with the new fn_args-driven binding
   style upstream examples use) pass it through `fn_args` and receive it as
   a body parameter, as in the SAXPY example
   (`programming_examples/getting_started/01_SAXPY/saxpy.py`).

5. **`rt.task_group()` / `rt.finish_task_group(tg)` become a standalone
   `TaskGroup` object**, imported from `aie.iron` (`from aie.iron import
   TaskGroup`). Construct it *inside* the sequence body —
   `tg = TaskGroup()` — it registers itself against the currently-active
   sequence via a context var, so it must be constructed while `seq_fn` is
   executing (i.e. inside the callback, not at module scope beforehand).
   Finish it with `tg.finish()` instead of `rt.finish_task_group(tg)`.
   If a design used the implicit default group (no explicit
   `task_group=`/`group=` at all), nothing needs to change there — the
   default group still auto-flushes at the end of the body.

6. **`Program(dev, rt)` becomes `Program(dev, rt, workers=[...])`.** This is
   the other half of point 3 — `Program.__init__` now takes the worker list
   explicitly as its third argument (default `None` = no workers), where it
   used to infer them from whichever `rt.start(...)` calls ran inside the
   `with` block.

## Import changes

`TaskGroup` needs adding to the `aie.iron` import line if the design uses
explicit task groups (most of ours do, since `wait=True` on a drain typically
needs to be grouped with a non-waited fill so both get freed together):

```python
from aie.iron import CompileTime, In, ObjectFifo, Out, Program, Runtime, TaskGroup, Worker
```

`rt.sequence`, `rt.start`, `rt.fill`, `rt.drain`, `rt.task_group`,
`rt.finish_task_group` no longer exist as `Runtime` methods — grep for
`rt\.` after migrating a file to confirm nothing old-API survived.

## A second discovered pattern: `fill`/`drain`'s `tile=` kwarg moved to `.prod()`/`.cons()`

Found migrating `cross_column_join_probe.py`, which pins a fill/drain to a
specific shim tile (needed when a design spans multiple physical columns and
the auto-assigned shim tile would be wrong). The OLD API took `tile=` as a
keyword directly on `rt.fill(...)`/`rt.drain(...)`:

```python
rt.fill(A_shims[col].prod(), A, tap=..., task_group=tg, tile=Tile(pcol, 0))
```

**`fill`/`drain` no longer accept `tile=` at all** (see their param list above
— it is not one of the surviving kwargs). Instead, pin it on the **handle**,
at `.prod(tile=...)`/`.cons(tile=...)` construction time, matching
`Runtime.__init__`'s docstring ("fifo shim endpoints bind now (from
`prod(tile=)`/`cons(tile=)`)"):

```python
A_prod = A_shims[col].prod(tile=Tile(pcol, 0))
...
def sequence(A, ..., A_prod_h, ...):
    A_prod_h.fill(A, tap=..., group=tg)
rt = Runtime(sequence, [..., A_prod, ...])
```

This matters because handle construction now happens *before* `Runtime()` is
even called (it has to — the handle is itself an `fn_args` entry), not inside
the sequence body as before.

## What did NOT change (confirmed by the pilot)

- `ObjectFifo(...)` construction, `.cons()`/`.prod()`, `Worker(core_fn,
  fn_args, stack_size=...)`, `TensorTiler2D`, `CompileTime`, `ExternalFunction`,
  `iron.set_current_device`/`from_name`, `@iron.jit` — all unchanged in the
  one file migrated so far (`exp2_probe.py`). Confirm per-file rather than
  assuming, per the task brief — `dataflow/objectfifo.py` grew 40% so other
  surfaces (`.join()`/`.split()`/`.forward()` kwargs in particular) may still
  have moved for files that use them; this note will be extended if/when a
  new pattern turns up in a later file.
- The JIT cache directory layout, `iron.jit(aiecc_flags=[...])`, and the
  overall dispatch/trace path (`get_trace_summary.py`, `parse.py`) are
  unaffected — this is a Python **design authoring** API change only. Already
  built `.xclbin`/`insts.bin` artifacts are static binaries and load under
  XRT regardless of what Python built them (per this task's scope discipline
  — production `runtime/artifacts_*` is untouched).

## Pilot verification

`experiments/m5-eltwise/exp2_probe.py` (smallest of the 15 affected files,
84 lines) migrated with exactly the six-point transform above. Built and ran
on hardware after a full JIT-cache purge
(`rm -rf ~/.npu/cache/*`): **max relative error 6.744e-03, median 1.068e-04**
over `x ∈ [-120, 0]` — matches the number already on record in
[`tasks/0021`](../../tasks/0021-m5-softmax-and-full-model/TASK.md) ("`exp2_probe`
measures max relative error **6.7e-03**") bit for bit at the reported
precision. No behavioural regression from the toolchain upgrade in this file.

## Full-sweep verification (tasks/0058)

The remaining 14 files were migrated and hardware-verified in a follow-up
session. All six transformation rules above held for every file — no new
`Runtime`/`ObjectFifo` API surface changes were found beyond the `tile=` move
already documented. Two NEW patterns turned up, neither in the `Runtime`
surface itself:

### The `aie.dma_bd` textual form changed, and it broke a downstream tool

Not a Python API change — a change to the MLIR pretty-printer's OUTPUT text.
In the sequence-body `aie.dma_bd` op, the old bracket-tuple form

```
<size = 64, stride = 48>
```

is now printed as a flat array:

```
sizes = [1, 12, 256, 48] strides = [0, 96, 1152, 1]
```

(confirmed directly by grepping a freshly-built `aie.mlir`). The OLD
bracket-tuple form still survives elsewhere in the same file — `ObjectFifo`
`dimensionsToStream` attributes still print `<size = N, stride = M>` — so a
blanket "does `<size = k, stride = n>` appear anywhere in this file" check
can silently go from matching (1.3.4) to never-matching (1.4.x) depending
entirely on WHICH op happened to be the one carrying the substring, with no
error raised anywhere. `tools/export_gemm_rtp.py`'s `markers_for()` hard-codes
the old sequence-body form and is broken by this (`0 cache candidates after
purge -- expected exactly 1`); it is not one of the 15 `Runtime`-based files
and was not fixed this session. Any other code that string-matches generated
MLIR text (as opposed to parsing it structurally) should be treated as
suspect after this upgrade, not just code that touches `Runtime` directly.

### A fourth instance of the marker-specificity stale-cache fail-open, this time inside `@iron.jit` itself

`experiments/m5-pretiled-gemm/cross_column_join_probe.py` defines its own
`markers_for()`/`purge()` (matching the pattern documented above for
`tile=`), and it worked correctly — it found 0 stale candidates when asked to
purge for a brand-new shape it had never built before. The stale hit came
from underneath that: `@iron.jit`'s OWN cache lookup (inside
`aie.utils.compile.jit.compilabledesign`, not this project's code) returned a
kernel compiled for a *different* run's tensor shape, caught only by
`validate_tensor_args`'s own runtime shape check (`RuntimeError: Tensor
argument 'A' has 32768 elements but the kernel was compiled for 8192
elements`) rather than silently returning wrong data — this specific case
fails loud, not quiet, unlike the other three instances of this bug class.
The mitigation is the same as always: `rm -rf ~/.npu/cache/*` before trusting
a result when a script's compile-time-relevant Python-level state (env vars,
CLI flags feeding into `CompileTime`-adjacent globals) changes between runs
in the same session, even when that script's own `purge()` reports 0
candidates.

`tasks/0058`'s own TASK.md has the per-file verification table and every
number re-derived this session.
