How source becomes something that runs on the NPU, on **this** machine, without WSL.

the native-Windows path, which is officially supported but marked *experimental*
upstream (`docs/buildHostWinNative.md`).

## Peano only — and what it costs

**Peano** (`llvm-aie`) is AMD's open-source LLVM backend for AI Engines. It registers
targets `aie`, `aie2`, `aie2p`, `aie2ps`. It is the **only** kernel compiler available
on native Windows; `xchesscc` (proprietary, Vitis) is Linux-only.

This is fine — AMD's own optimisation guidance (`skills/aie-kernel-opt/SKILL.md`) is
Peano-centric, and Peano is now the majority path in mlir-aie's own test suite
(20 Peano lit tests vs 9 Chess).

**What we lose:**

| Lost | Impact |
|---|---|
| Native **bfp16** kernels (`mm_bfp.cc`, `ml/block_datatypes/`) | The theoretical peak mode is unreachable |
| `--aiesim` | No simulator; hardware or nothing |
| Chess-style modulo scheduling | Historically tighter VLIW code; gap has narrowed |
| `chess_prepare_for_pipelining` semantics | Peano's equivalent is a **trip-count hint only** — it still emits a runtime loop |

**What we keep:** `--emulate-bf16-mmul-with-bfp16`
(`-DAIE_API_EMULATE_BFLOAT16_MMUL_WITH_BFP16`) is **Peano-compatible** and upgrades
bf16 matmul geometry from `4×8×8` to `8×8×8`. That is a 2× MAC improvement from one
flag, and it is an early experiment in M2.

**Known risk:** mlir-aie issue **#2411, "GeMM Failing Shapes on Strix for bf16"** —
Peano struggles with some non-power-of-two shapes where Chess succeeds. Our shapes
(384 / 1152 / 1536, all multiples of 64) should be safe, but this is the first thing
to suspect if a GEMM fails to compile.

Peano also lacks `<adf.h>` (Vitis-only), which is why every kernel compile passes
`-D__AIE_API_AIE_ADF_HPP__` to stop `aie_api` from including it.

**Peano and Chess cannot be mixed in one design** — `compilabledesign.py` collects
`{f._use_chess for f in external_kernels}` and raises on a mixed set.

## The compilation pipeline

```
Python function with @iron.jit
   │  captures generator + CompileTime params + flags
CompilableDesign            ── recipe_hash (cache key) + artifact_hash (freshness)
   │  _generate_mlir  (runs the generator exactly once)
MLIR module
   │  Peano clang++ compiles each kernel .cc -> .o
   │  aiecc.exe: aie-opt -> aie-translate -> link -> bootgen
final.xclbin + insts.bin (and optionally insts.elf)
   │  cached under $NPU_CACHE_HOME
NPUKernel: xrt::hw_context + xrt::kernel -> run()
   │
  NPU
```

**Kernel compile** (`python/utils/compile/utils.py`):

```
%PEANO_INSTALL_DIR%\bin\clang++ <kernel.cc> -c -o <kernel.o>
  -I%MLIR_AIE_INSTALL_DIR%\include
  -std=c++20 -O2 -DNDEBUG -D__AIE_API_AIE_ADF_HPP__
  -Wno-parentheses -Wno-attributes -Wno-macro-redefined -Wno-empty-body
  --target=aie2p-none-unknown-elf
```

**Design compile:**

```
aiecc.exe <work_dir>\aie.mlir
  --no-compile-host --no-xchesscc --no-xbridge --peano=%PEANO_INSTALL_DIR%
  --aie-generate-npu-insts --npu-insts-name=<insts.bin>
  --aie-generate-xclbin    --xclbin-name=<final.xclbin>
  [--aie-generate-elf --elf-name=<insts.elf>]
  --tmpdir=<work_dir>
```

> **`aiecc.py` is now a 114-line shim over the C++ `aiecc.exe`**; `aiecc.run()` is
> deprecated. Any blog describing `aiecc.py`'s Python internals is out of date. The
> shim uses `shutil.which("aiecc")`, so `MLIR_AIE_INSTALL_DIR\bin` must be on PATH.

### The build cache

`$NPU_CACHE_HOME`, default `C:\Users\<user>\.npu\cache\<recipe_hash>\`. Contents:

```
aie.mlir                       input_with_addresses.mlir   <- needed for tracing!
final.xclbin                   insts.bin
main.pdi                       main_design.bif
main_aie_cdo_{init,elfs,enable}.bin
main_aie_partition.json        main_kernels.json          main_mem_topology.json
main_core_<col>_<row>.{elf,o,ll,opt.ll,peano-compat.ll,ld.script}
<kernel>.cc  <kernel>.o        params.txt
```

`main_core_*.peano-compat.ll` is a workaround IR stage for Peano intrinsic-lowering
gaps — its presence is normal.

Force a rebuild with `@iron.jit(..., use_cache=False)` or by deleting the cache dir.
See every command executed with:

```python
import logging; logging.getLogger("aie.utils.compile").setLevel(logging.DEBUG)
```

## How to actually build and run

> ⚠️ **`make` will not save you.** `mingw32-make` 4.4.1 exists, but the
> `programming_examples` Makefiles assume POSIX (`mkdir -p`, `rm -rf`, backticks) and
> carry `${powershell}` / `${getwslpath}` hooks for the WSL flow. MinGW's value here is
> real `make` for **our own** build files, plus gcc/g++ for `-fsyntax-only` checks.

**Simplest — the design compiles and runs itself:**

```powershell
cd C:\dev\mlir-aie\programming_examples\getting_started\01_SAXPY
python saxpy.py
```

**The Makefile-equivalent driver:**

```powershell
cd programming_examples\basic\vector_scalar_mul
python ..\..\..\utils\run_example.py build
python ..\..\..\utils\run_example.py run
python ..\..\..\utils\run_example.py trace
```

Actions: `build | run | run_py | trace | trace_py | host | clean`. It handles
multi-config generators (VS puts the exe in `_build\Release\`, Ninja in `_build\`).

Host invocation convention:
`<target>_<size>.exe -x <xclbin> -i <insts> -k MLIR_AIE [-t <trace_size>]`

## The C++ host (M7)

**Do not vendor XRT.** mlir-aie vendors none of it; `C:\Xilinx\XRT` is the real SDK.

| Artifact | Path |
|---|---|
| Headers | `C:\Xilinx\XRT\include\xrt\{,experimental,detail}` |
| Import lib | `C:\Xilinx\XRT\lib\xrt_coreutil.lib` |
| **Runtime DLL** | `C:\Windows\System32\xrt_coreutil.dll` — **driver-installed and signed** |
| CMake package | `C:\Xilinx\XRT\share\cmake\XRT\xrt-config.cmake` |

Nothing to do about DLL search paths — `xrt_coreutil.dll` lives in `System32`.

```cmake
cmake_minimum_required(VERSION 3.30)
set(CMAKE_CXX_STANDARD 23)
include(<mlir-aie>/programming_examples/mlir_aie_init.cmake)
mlir_aie_init_example()        # adds /Zc:__cplusplus on Windows
project(${ProjectName})        # <-- MUST come before common.cmake
include(<mlir-aie>/programming_examples/common.cmake)   # find_package(XRT)

add_executable(${currentTarget} test.cpp)
target_include_directories(${currentTarget} PUBLIC ${XRT_INC_DIR})
target_link_directories   (${currentTarget} PUBLIC ${XRT_LIB_DIR})
target_link_libraries     (${currentTarget} PUBLIC xrt_coreutil)
target_link_test_utils(${currentTarget})
```

> ⚠️ **`project()` must precede `find_package(XRT)`** — `xrt-targets.cmake` calls
> `add_library(... SHARED IMPORTED)`, which without a prior `project()` either fails
> with *"does not support dynamic linking"* or **silently downgrades to STATIC**
> (mlir-aie issue #3048).

> ⚠️ `common.cmake`'s Windows fallback paths are stale junk
> (`C:/Technical/XRT/...`, `C:/Technical/xrtNPUfromDLL`). If `find_package(XRT)` misses,
> you get those and a confusing include error. **Always check `XRT_INC_DIR` in
> `CMakeCache.txt`.**

> ⚠️ `/Zc:__cplusplus` is required — without it MSVC reports `__cplusplus == 199711L`
> and `aie_api`'s C++20 detection breaks. `mlir_aie_init_example()` adds it.

Two host styles exist. Prefer the modern one for new code:

- **Modern** (`programming_examples\ml\eltwise_unary\test.cpp`): `xrt::elf` +
  `xrt::module` + `xrt::ext::kernel`. No manual instruction-BO management.
- **Classic** (`runtime_lib\test_lib\xrt_test_wrapper.h`): explicit `xrt::bo` with the
  argument contract `arg0=opcode(3)`, `arg1=instr BO`, `arg2=instr count`,
  `arg3..arg7 = inout0..4` at `group_id(3)..group_id(7)`. Gives trace plumbing for free.

Prebuilt helper library (no need to compile it):
`ironenv\Lib\site-packages\mlir_aie\runtime_lib\x86_64\test_lib\` — `test_utils.h`,
`xrt_test_wrapper.h`, `cxxopts.hpp`, `test_utils.lib`, plus a `bfloat16_t` shim.

## Windows gotchas, collected

1. **`make` doesn't fix the example Makefiles** (see above).
2. **`XILINX_XRT` must stay unset**; use `XRT_ROOT`.
3. **Python pinned to 3.13** by `pyxrt.pyd`.
4. **`. .\iron_env.ps1` must be dot-sourced.**
5. **Peano is deliberately off PATH** so its `clang.exe` doesn't shadow MSVC/host clang.
   Reference it as `$env:PEANO_INSTALL_DIR\bin\clang++.exe`.
6. **`aiecc.py` is a shim** needing `MLIR_AIE_INSTALL_DIR\bin` on PATH.
7. **CMake `project()` ordering** (#3048).
8. **Stale `C:/Technical/...` fallbacks** in `common.cmake`.
9. *"Could not find any instance of Visual Studio"* — an older CMake earlier on PATH
   (Strawberry Perl and conda are known culprits). Fix PATH order **and delete the
   build dir** (CMake caches).
10. **Spectre errors MSB8042 / `/Qspectre`** — XRT forces it; install the
    "C++ x64/x86 Spectre-mitigated libraries" VS component.
11. **CMake finds the wrong Python** — activate the env *before* configuring, then wipe
    the build dir.
12. **Missing DLLs at tool startup** — install "Visual C++ 2015-2022 Redistributable (x64)".
13. **Device mismatch** — building an `aie2` (Phoenix) xclbin and loading it on Strix is
    the likeliest cause of an xclbin/device error. Keep `NPU2=1` / `--dev npu2` consistent.
