# models — матрица контейнеров по вариантам точности

72 файла из 72 возможных (18 моделей × 4 варианта), собраны
`tools/pack/pack_npue.py` 8 октября 2026. Варианты лежат в `models/`
плоско, рядом с установленными контейнерами: рантайм резолвит имя
точным совпадением `models/<имя>.npue`, поэтому 18 установленных
имён не меняются, а вариант адресуется по имени
(`npuembeddings embed all-MiniLM-L6-v2.i4`) или по пути и виден в
`list` в разделе «Locally packed».

Варианты:

| код | что это |
|---|---|
| `f32` | базовый тип в модели (fp32); для GEMM-архитектур — host-only контейнер |
| `bf16` | операнд массива (по умолчанию пакера) |
| `i8` | int8, W8A8 |
| `i4` | int4, W4A8 поверх того же int8-массива |

## Канонические контейнеры (10)

В `models/` лежат и сами установленные контейнеры —
`models/<имя>.npue` без суффикса: семь GEMM-моделей
(all-MiniLM-L6-v2, bge-base-en-v1.5, embeddinggemma-300m,
whisper-tiny, whisper-base, vit-base-patch16-224,
nomic-embed-text-v1.5) — bf16, и три свёрточных
(yolov8n-pose, mediapipe-hands, mediapipe-pose) — f32 с
панелями для массива (`--npu`). Это файлы, которые `list`,
`discover_models`, `tools/pipeline.py check` и
`verify_npu_op_matrix.py` ищут по каноническому пути: пока
ни одного нет, гейт оп-матрицы краснеет с «ran 0 cells»,
а его строки «not on this machine» врут — файла нет не
из-за машины, а потому что его нет. Размеры — те же, что в
столбцах bf16 и f32 выше: канонический контейнер и есть
умолчание пакера (bf16 для GEMM, f32 для свёрточных),
упакованное 8 октября 2026 текущим пакером.

Замер для честности: ключ `gemm_layout` в конфиге появился
в пакере в той же сессии (для f32-host контейнеров), поэтому
из 72 вариантов несут его только 15 f32 GEMM-вариантов и
три файла embeddinggemma-300m (последние, упакованные после
правки); остальные 45 bf16/i8/i4-вариантов — без него. Ключ
опционален: рантайм читает его отсутствие как
`pretiled_bf16`, и без него прогнаны все 144 прогона и гейт
оп-матрицы — 8 октября в 16:46 он был зелёным на контейнерах,
упакованных до появления ключа. Свежая упаковка пишет его
всегда: все семь канонических GEMM-контейнеров несут его,
свёрточные не несут по определению.

## Три факта о свёрточных архитектурах (6/7/8), которые стоит знать перед выбором i4

1. **i8 — единственная сжимающая точка.** На всех трёх архитектурах
   int8-весы дают файл меньше f32 с измеримой, но честно заявленной
   ценой (hands: bbox 8.0 px от записи zoo; mppose: landmarks в среднем
   52 px, худший 87.5 px — far-side foot/ankle/heel/knee, где ресемплер
   и сеть расходятся больше всего).

2. **i4 на arch=7/8 живёт только при группе 1, и при этом БОЛЬШЕ f32.**
   Замер на gate-кадрах (`hand_plain.png`, `docs/bus.jpg`), рантайм
   против рантайма f32:

   | группа | hands | mediapipe-pose |
   |---|---|---|
   | 8 (бывший дефолт) | **0 рук** | **0 людей** |
   | 4 | **0 рук** | **0 людей** |
   | 2 | 1 рука, landmarks 12.9 px (бюджет 2.5) | **0 людей** |
   | 1 | 1 рука, худшее 0.007 px | 1 поза, keypoints 0.04 px |

   Группа 1 — lossless (один масштаб на вес, четыре бита точны), но
   файл 14.8 / 33.5 МБ **против** 13.3 / 30.2 МБ у f32: байт масштаба
   на каждый вес дороже тех четырёх бит, которые он заменяет. Поэтому
   дефолт `--dtype i4` для arch=7/8 — группа 1 (рабочий, lossless,
   но без выигрыша по размеру), а сжимающая точка — i8. Это то же
   самое, что arch=6 измерила раньше: «i8 — единственная точка,
   которую стоит иметь». Другую группу выбирает `--int4-group N`;
   пакер печатает эту таблицу при упаковке.

3. **bf16 conv-весы** (все три архитектуруры) — отдельный путь в
   `tools/lib/conv_quant.py`: веса хранятся как bf16-панели, рантайм
   расширяет их до f32 перед свёрткой. hands bf16: 9.5 МБ, дельты
   от zoo 1.9 px bbox / 3.5 px landmarks.

Квантованные conv-контейнеры (i8/i4/bf16) **измеряются, а не гейтятся**
на f32-толерантностях: `verify_hands.py` / `verify_mppose.py` печатают
пост-профили отклонений против onnxruntime и записей zoo и говорят
«MEASURED, NOT GATED»; контейнер, который ничего не находит, говорит
про это прямо (сейчас таких в наборе нет — после перехода на группу 1).

## Как это собрано

    python tools/pack/pack_npue.py --model-dir models/<имя> \
        --out models/<имя>.<вариант>.npue --dtype <вариант>

Свёрточные архитектуры берут ONNX-файл/каталог напрямую и всегда с `--npu`
(в них дополнительно укладываются панели для массива):

    --pose-onnx models/yolov8n-pose/yolov8n-pose.onnx   # arch=6
    --hands-onnx models/mediapipe-hands                 # arch=7
    --mppose-onnx models/mediapipe-pose                 # arch=8

Все три принимают `--dtype f32|bf16|i8|i4` (и `--int4-group N` для i4).
Непрописанный dtype для свёрточных архитектур — f32, точность самого
чекпоинта, а не глобальный `bf16` пакера.

Исключение по геометрии: **bge-large-en-v1.5 требует `--tile-n 32`** — его
N=1024 не делится на 48 (остальные модели встают на значение по умолчанию,
whisper форсирует 32 внутри своего пакера). Дизайны под bge-large действительно
экспортированы с `tile n=32`, хеш макета собирается с ними: `4d729172…` (bf16)
и `f0a4a896…` (i8).

Каждый контейнер несет свой дизайн внутри (набор берется из
`runtime/artifacts/<имя>` или `<имя>-i8` для int8/int4), поэтому файл самодостаточен.

## Проверки

- прогон каждого контейнера рантаймом, дважды — на хосте и на массиве
  (`--npu-ops gemm` для GEMM-архитектур, `--npu-ops conv` для arch=6/7/8):
  прогонов **144** (72 контейнера × хост и массив), падений **0**;
  ненулевых **15**, и все 15 — отказы по дизайну: массиву по имени
  предложен host-only f32-контейнер (rc=2, ожидаемо, имя операции в
  сообщении);
- `verify_pose_streamset.py` для yolov8n-pose.bf16: PASS (in-repo половина;
  дизайн-сет требует MLIR-AIE, которого на этой машине нет);
- `verify_hands.py` / `verify_mppose.py` для всех четырёх вариантов каждой
  из двух моделей: rc=0, измеренные дельты в логах;
- `verify_conv_quant.py` для yolov8n-pose.i4: PASS (C++ reader и пакер
  согласны бит-в-бит);
- `verify_pack_parity.py`: PASS, байт-в-байт (npu1 и npu2).

Чего здесь **нет**: измерений скорости на массиве для этих файлов — я их
не мерил. Массивные цифры в README относятся к установочным контейнерам,
а не к этому набору.

## Правки, которые потребовались (иначе часть файлов не собиралась бы или гейт не был бы зелёным)

1. `pack_gte`: `a_dtype` был жестко `bf16`, тогда как панели уже писались I8 —
   контейнер противоречил сам себе; плюс не писал вовсе `int4_group`, из-за
   чего `--dtype i4` выдавал файл, который рантайм не открывает
   («the container states no int4_group»).
2. `pack_whisper`: набор дизайна подшивался с жестким datapath `bf16`, то есть
   в int8-контейнер клался bf16-дизайн.
3. `pack_vit`: та же жесткая `bf16`.
4. C++ `prepare_model` (BERT-пакер в `runtime/src/common/npue_pack.cpp`) не
   писал `gemm_layout` — Python-пакер пишет его в этой же позиции, и два
   пакера сравниваются байт-в-байт (`verify_pack_parity.py`), так что после
   host-only f32-контейнеров гейт падал на 30 байтах конфига. Теперь пишет
   (`"pretiled_bf16"` — этот пакер только их и производит).
5. `POSE_I4_GROUP_DEFAULT` перестал быть одним числом на три архитектуры:
   arch=6 оставил 8 (последняя точка перед своим обрывом), arch=7/8 получили
   1 — свою единственную точку с детекцией (таблица выше).

Правки 1–3 задевают только int8/int4 ветки: bf16-сборка не изменилась, о чём
свидетельствует `verify_pack_parity` (байт-в-байт с C++-пакером).
