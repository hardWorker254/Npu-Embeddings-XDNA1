# NpuEmbeddings -- build-time Python requirements.
#
# Build-time ONLY. Nothing here is used at runtime: the runtime is C++, and a
# release contains no Python at all (BUILD.md §1).
#
# This file is the HUMAN-READABLE list -- the packages this project asks for,
# and why. The exact bytes a build is known to work with are in
# requirements.lock.txt, which is what bootstrap.sh installs. Bump a pin here,
# then re-freeze.
#
# Targets Python 3.14 on x86_64. The MLIR-AIE wheels are built per-ABI (cp314,
# cp313, cp312, cp311), so a different Python needs a different tag in
# requirements.amd.txt.

# The extra index torch's +cpu wheels live on. PyPI's torch is the CUDA build
# (a much larger wheel, and useless here -- there is no NVIDIA device).
--extra-index-url https://download.pytorch.org/whl/cpu

# --- the webcam pose demo ------------------------------------------------
# opencv-python  examples/pose_webcam.py -- capture a webcam and draw the
#          skeleton. The FULL package and not opencv-python-headless, because
#          the demo's whole point is cv2.imshow: headless has VideoCapture and
#          not the window, so the headless wheel would install cleanly and then
#          refuse at the one call the user came for. That choice costs something
#          on a machine with no desktop -- the full wheel links libGL, so
#          `import cv2` on a bare server dies with "libGL.so.1: cannot open
#          shared object file" unless libgl1 is present. It is a build-time
#          requirement like everything else here, so this is the cost of putting
#          a demo in the default set rather than the cost of the runtime, which
#          is C++ and has none of it.
#
#          The wheel is cp37-abi3, so one artifact serves 3.11 through 3.14 and
#          does not need an AIE_ABI-style pin per interpreter. It adds NO new
#          transitive requirement -- its only dependency is numpy, already
#          pinned above -- so this is one line in the lock. Verified: `pip
#          freeze` gains only opencv-python, and `pip check` still reports
#          nothing but the pre-existing llvm-aie platform note.
opencv-python==5.0.0.93

# --- reading .onnx checkpoints --------------------------------------------
# onnx     parses a graph's initializer + node names, and is the REFERENCE the
#          weight reader is checked against. Build-time only, like everything
#          here: it is never imported by the runtime. Four requirements --
#          numpy, protobuf, ml-dtypes and typing-extensions -- and the first
#          three are pinned above already; typing-extensions arrives anyway (it
#          is pydantic's), so this adds one line to the lock and nothing new to
#          the resolution. Verified by `pip freeze`: the lock is unchanged
#          apart from onnx==1.23.1. 1.23.1 is a cp312-abi3 wheel on Python
#          3.14; opset 28.
#
#          WHY THE READER ITSELF DOES NOT IMPORT IT. tools/lib/onnx_weights.py
#          walks the protobuf wire format by hand instead, because onnx.load()
#          materialises the entire file: measured on this machine, 212 MB
#          resident for a 90 MB model, i.e. 2.35x the file -- and whisper-large
#          is 3.1 GB, which would be a 7 GB spike the hand-written reader was
#          written to avoid. The cost of hand-rolling is that a wrong field
#          number would be SILENT (protobuf returns a different tensor rather
#          than complaining), so onnx earns its place in the other direction:
#          tools/verify/verify_onnx_reader.py compares every hardcoded field
#          number against the descriptors of this exact package, cross-checks
#          the reads against onnx.load(), and then proves the gate can fail.
onnx==1.23.1
