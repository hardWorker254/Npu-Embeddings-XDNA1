# NpuEmbeddings (на русском)

Эмбеддинги предложений для моделей семейства BERT на AMD NPU, с хостовым CPU
как запасным путём. `serve` — HTTP-эндпоинт в форме OpenAI, `embed` — файл в
файл. Плюс распознавание речи: Whisper целиком на массиве, все GEMM, и по
флагу `--npu-extra-ops` ещё семь операций.

Оригинал на английском — [README.md](README.md). Этот файл не перевод
построчный, а то же дерево по-русски; числа и команды те же.

Дерево нацелено на **XDNA1 / `npu1` на Linux**. Поколение выбирается флагом
`--dev`, а набор дизайнов записывает, для какого он построен, и набор от
другого поколения **отвергается**, а не загружается.

## Требования

| | |
|---|---|
| Железо | AMD Ryzen AI, поколение `npu1` (XDNA1). 16 ядер, **6** одновременных `hw_context` |
| ОС | Linux с установленным драйвером XDNA |
| Инструменты | `mlir-aie` (Python), Peano для компиляции ядер AIE |
| Сборка рантайма | g++ 17 или новее, CMake, libcurl |
| Python | 3.10+ для экспортёров и для гейтов |

```bash
source /opt/xilinx/xrt/setup.sh
export PEANO_INSTALL_DIR=<путь к llvm-aie>   # без него экспортёр падает
```

`PEANO_INSTALL_DIR` обязателен: без него `mlir-aie` завершается
`RuntimeError: Invalid Peano install directory: peano_not_found`.
`/opt/xilinx/xrt/setup.sh` его **не** выставляет.

## Быстрый старт

### 1. Контейнер и наборы дизайнов

```bash
# 1. контейнер. Для whisper --max-seq передавать НЕ надо: по умолчанию берётся
#    max_source_positions самого чекпойнта (1500).
python tools/pack/pack_npue.py --model-dir models/all-MiniLM-L6-v2 \
    --out models/all-MiniLM-L6-v2.npue --device npu1

# 2. набор дизайнов. Одна команда пишет и encoder, и decoder: у whisper их M
#    отличается в 8 раз, один xclbin не обслуживает оба.
python tools/export/export_gemm_rtp.py --target all-MiniLM-L6-v2 --arch 1
```

Для whisper оба набора обязательны: `gemm_rtp` (эндокодер) и `gemm_rtp_dec`
(декодер). Набор только с одной половиной отвергается по имени.

### 2. Рантайм

```bash
cd runtime/build
rm -rf CMakeFiles CMakeCache.txt && cmake .. && make -j8
```

**`rm -rf CMakeFiles CMakeCache.txt` — не педантизм.** Обычный `make` перестаёт
пересчитывать зависимости от заголовков: правка `run_setup.hpp` или
`stt_mode.hpp` даёт «Built target» и бинарник без правки. Отсутствие ошибки в
выводе сборки здесь ничего не значит — проверяйте `strings`, `nm` или дату
бинаря. Проверяйте и размер сразу после сборки, а не потом: файловая система на
этой машине несколько раз возвращала выход сборки к предыдущему.

Сборка даёт **один** бинарь — `runtime/build/npuembeddings`. Раньше их было два:
таргет назывался `npuembed`, а `npuembeddings` был его `POST_BUILD`-копией, так
что имя, которое собиралось, и имя, которое запускали, не совпадали.

### 3. Запуск

```bash
# что установлено и что может работать
./runtime/build/npueembeddings list

# эндпоинт в форме OpenAI на 127.0.0.1:8080
./runtime/build/npueembeddings serve models/all-MiniLM-L6-v2.npue

# батч: одно предложение в строке -> матрица fp32
./runtime/build/npueembeddings embed all-MiniLM-L6-v2 in.txt out.f32

# распознавание речи
./runtime/build/npueembeddings transcribe whisper-tiny audio.wav
```

## Как выполняется запрос

1. **Токенизация** на хосте: WordPiece, BPE или по таблице whisper.
2. **Выбор батч-тира** — наибольший, в который запрос помещается; у набора
   дизайнов свой поток инструкций на тир.
3. **Слой за слоем**: эмбеддинги → `qkv` → attention → `attn_out` → `ffn_up` →
   GELU → `ffn_down` → следующий слой. Четыре GEMM каждого слоя — четыре
   диспатча на тир, плюс `bf16`-упаковка A и распаковка C на хосте.
4. **Пулинг и L2-нормализация** на хосте.
5. **Сверка** с эталоном HuggingFace в том же процессе, порог
   `worst 1 - cos ≤ 2e-3`. Без Python.

## Где что выполняется

| Операция | По умолчанию | На массиве при | Цена |
|---|---|---|---|
| GEMM: qkv, attention-out, ffn-up, ffn-down, cross-q, cross-K\|V | массив | всегда | — |
| conv1, conv2 (Whisper) | хост | `--npu-extra-ops conv` | контекста не стоит: поток `[rows, d, d]` самого энкодерного набора |
| attention, как GEMMы QK^T и softmax·V | хост | `--npu-extra-ops attn` | контекста не стоит: два потока в тех же наборах |
| банк mel-фильтров, как GEMM | хост | `--npu-extra-ops mproj` | контекста не стоит: один поток в энкодерном наборе |
| трансформация 400 точек, как GEMM | хост | `--npu-extra-ops fft` | контекста не стоит: один поток в энкодерном наборе |
| проекция связанного эмбеддинга в словарь | хост | `--npu-extra-ops logit` | контекста не стоит: восемь потоков-чанков; 39 МБ панелей |
| LayerNorm | хост | `--npu-extra-ops layn` | один `hw_context` (`layernorm/`) |
| softmax | хост | `--npu-extra-ops softm` | один `hw_context` (`softmax/`) |
| GELU (точный erf) | хост | `--npu-extra-ops gelu` | один `hw_context` (`gelu/`) |

Один флаг, и операция на хосте **ровно тогда**, когда её нет в списке.
Обратного флага нет: две записи для одного состояния — это ровно тот способ,
которым флаг и его инверсия расходятся. Старые имена (`--npu-ops`,
`--npu-eltwise`, `--host-ln`, `--host-sm`, `--host-gelu`) **отвергаются по
имени**, чтобы устаревшая командная строка не выглядела работающей.

GEMM-образные коды (`conv`, `attn`, `mproj`, `fft`, `logit`) не требуют
собственного набора дизайнов: это поток внутри уже существующего набора, поэтому
они не стоят `hw_context`, и набор без них **отвергается по имени**, а не
отвечает с хоста. Элементарные требуют своего xclbin каждый, так что все три —
это пять контекстов из шести.

**Что из этого стоит просить — измерение, а не вкус.** См.
[Что выносить на NPU](#что-выносить-на-npu).

## Что выносить на NPU

Три разных вопроса — три разных ответа, и наборы операций у них разные. Все
числа ниже **измерены на этой машине**: `whisper-tiny` (d=384, 4+4 слоя, 6
голов), тон 440 Гц длиной 3 с, 16 хостовых потоков, один и тот же бинарь, из
которых ~0.35 с — настройка. `CPU` — суммарное пользовательское время всех
потоков; это число важно, когда scarce — процессор. `wall` — то, что
ждёт вызывающий.

| `--npu-extra-ops` | wall, с | CPU, с | энкодер, с | декодер, с | диспатчи |
|---|---:|---:|---:|---:|---:|
| *(ничего — всё на хосте)* | 0.94 | 5.54 | 0.28 | 0.07 | 192 |
| `conv` | **0.66** | **3.81** | 0.30 | 0.07 | 207 |
| `conv,mproj,fft` | **0.65** | **3.49** | 0.30 | 0.07 | 219 |
| `conv,mproj,logit` | 0.77 | 3.94 | 0.28 | 0.07 | 253 |
| `layn` | 1.05 | 5.57 | 0.36 | 0.28 | 284 |
| `gelu` | 1.22 | 5.04 | 0.43 | 0.33 | 224 |
| `conv,mproj,layn,gelu,logit` | 1.56 | 3.62 | 0.52 | 0.53 | 377 |
| `conv,attn,softm` | 4.32 | 2.46 | 1.01 | 2.88 | 1143 |
| `conv,attn,mproj,fft,logit,layn,softm,gelu` | 4.90 | **1.05** | 1.21 | 3.35 | 1319 |

Разброс от прогона к прогону на этой машине: несколько процентов по wall и до
10% по CPU. Читайте отношения, а не последнюю цифру.

### 1. Максимальная производительность: `conv`, и только `conv`

`conv` — единственная операция, которая выигрывает **по обеим** осям, и причина
структурная: её работа это d² MAC, то есть стоимость на хосте растёт как
квадрат ширины, а на массиве — как число диспатчей, то есть не растёт. На окно
30 с и 16 хостовых потоков: 0.11 с → 0.02 с при d=384, 1.37 с → 0.07 с при
d=1280. Измеренные 0.94 → 0.66 s wall и 5.54 → 3.81 s CPU на whisper-tiny — то
же отношение на коротком окне, и с ростом ширины оно **улучшается**.

GEMM-ы уже там: они и есть модель, и ради них массив. Всё остальное — хостовая
работа, у которой арифметика мала рядом с числом диспатчей.

### 2. Баланс скорости и загрузки ЦП: `conv,mproj,logit` — или просто `conv`

`mproj` — это 48M MAC на окно, ~5 мс хоста и 6 диспатчей: на этой ширине
бесплатно, и заодно убирает самый большой хостовый цикл фронтенда. `logit` по
wall нейтрален (времена энкодера и декодера не двигаются): хостовый matvec и
восемь диспатчей стоят примерно одинаково. Он покупает 39 МБ панели bf16 — имеет
смысл, только когда scarce — процессор.

`layn` и `gelu` — контрпример, и причина у них одна: **работа на диспатч должна
перекрывать сам диспатч**. Диспатч `layn` покрывает 512 строк по 384 колонки, а
хост делает те же 196k элементов за 0.08 с на 16 потоках — стоимость диспатча и
round trip через bf16 того же порядка. В декодере хуже: там один LayerNorm —
это **одна строка**, 0.07 → 0.28 с, вчетверо хуже, потому что 511 из 512 строк —
падинг.

### 3. Максимальная экономия ЦП при приемлемой производительности: всё

Все восемь кодов: **1.05 с CPU против 5.54 с** — в 5.3 раза меньше — ценой
4.90 s wall против 0.94 с. Это честный размен: процессор перестаёт делать
упаковку в bf16, fp64-работу и подготовку панелей, а массив вместо этого делает
диспатчи.

Середина — `conv,mproj,layn,gelu,logit`: 1.56 s wall (в 1.7 раза медленнее) на
3.62 s CPU (на 35% меньше). Это набор, когда транскрипт может прийти на 60%
позже, а ядро нужно освободить под что-то ещё. `conv,attn,softm` — другой
конец: 4.6x к wall и минус 56% CPU.

### Сколько стоит attention и почему

Attention — самая большая арифметика в модели (184 GFLOP на окно) и **худшая**
кандидата для переноса на эту ширину: 0.28 → 1.01 с у энкодера и 0.07 → 2.88 с у
декодера. Число диспатчей — очевидная часть (головы × чанки × 2 × слои, 144 на
слой у whisper-tiny), но не вся стоимость. B-операнд оценки — это **активация**
(строки K и V слитого qkv), а не вес, поэтому его нельзя положить один раз на
сессию: он пересобирается заново для каждой головы каждого слоя, по 196k
элементов `tile_b_panel` каждый, и вот этот хостовый цикл и есть почти всё
измеренное время. GEMM с весовым B — это разовая подготовка; GEMM с
активационным B платит за укладку на каждом слое.

FFT — другой конец того же размена и единственная операция, которая не просто
медленнее. `dft400` — прямая трансформация как GEMM против предвычисленной
матрицы вилок в bf16, а значит у неё есть **шумовой пол** порядка (bf16 eps)² от
самого громкого бина. Громкие бины совпадают с хостом до 0.2%, а тихие
mel-каналы — те, что иначе прижал бы пол — читаются как 0.3 там, где хост даёт
3e-5. Он на массиве потому, что может там быть, и выключен по умолчанию
потому, что это другая спектрограмма; починка — fp32-ядро radix-400, а это
исследование, не разводка.

### Правило, которое из этого следует

1. Измеряйте **работу на диспатч** против фиксированных ~150 мкс. Операция, у
   которой на диспатч меньше арифметики, чем это, — хостовая работа.
2. Считайте **B-операнд**. Вес кладётся один раз; активация пересобирается на
   каждом слое, и укладка остаётся на хосте независимо от того, где считается
   умножение.
3. Проверяйте **падинг**. Дизайн считает все свои строки; построчная операция,
   которой дали одну строку работы, платит за весь буфер в обе стороны.
4. Смотрите на **собственную параллельность хоста**, прежде чем назвать
   хостовый цикл медленным. 16 потоков AVX2 бьют один столбец AIE на всём,
   кроме большого GEMM.

## Справочник по командной строке

`npuembeddings --help` авторитетен и синхронизирован с этим разделом.

### Подкоманды

| | |
|---|---|
| `serve` | `npuembeddings serve <модель> [--port N] [--bind ADDR]` — эндпоинт `/v1/embeddings`; модель докачивается сама, если её нет |
| `embed` | `npuembeddings embed <модель> <in.txt> [out.f32]` — батч, одно предложение в строке |
| `list` | что установлено и что может работать |
| `transcribe` | `npuembeddings transcribe <модель> <audio.wav>` (arch=4) |
| `add` | `npuembeddings add <org/model> [<sha256>]` — добавить в установку модель, которой нет в сборке |

### Опции `serve` / `embed`

| | |
|---|---|
| `--threads N` | бюджет хостовых потоков (по умолчанию 24 для serve/embed) |
| `--pipeline N` | полос в конвейере; `--threads 8 --pipeline 4` даёт каждой по 2 |
| `--dev npu1\|npu2` | поколение NPU |
| `--artifacts DIR` | набор дизайнов, если нестандартный путь |
| `--npu-extra-ops CODES` | что отправить на массив |
| `--dev` | поколение; записывается в `design.json` |

### Почему безопасные умолчания именно такие

- **Пустой `--npu-extra-ops` — это хост.** Замерено: построчная операция этой
  ширины на хосте быстрее. Флаг существует, чтобы поднять конкретную операцию,
  а не чтобы ускорить всё сразу.
- **Один `hw_context` на операцию.** Драйвер npu1 разрешает шесть; whisper уже
  занимает два (GEMM-наборы), три элементарных дают пять. Шестой слотов не
  остаётся ни на что.
- **Бюджет контекстов проверяется до постройки.** `require_context_budget`
  спрашивает `xrt-smi`, сколько контекстов занято, и отказывается по имени, если
  не влезает. `--allow-contention` отменяет проверку; число из запуска с
  конкуренцией не есть утверждение о производительности NPU.
- **Отчёт о контекстах идёт в stderr.** Для STT-режима stdout несёт только
  транскрипт (или JSON-объект с `--json`), и строка отчёта перед JSON делала бы
  его нечитаемым.

## Распознавание речи

### Что пользователь скачивает

Контейнер `.npue` (веса плюс шесть файлов на модель) и **два** набора дизайнов.
Только весов недостаточно: контейнер без наборов — это модель, которая
отказывает по имени.

### Три шага, один раз на модель

```bash
python tools/pack/pack_npue.py --model-dir models/whisper-tiny \
    --out models/whisper-tiny.npue --device npu1

python tools/export/export_gemm_rtp.py --target whisper-tiny --arch 1

./runtime/build/npueembeddings transcribe whisper-tiny audio.wav
```

Чтобы операции шли на массив, код добавляется в **оба** вызова — экспортёр
собирает потоки, рантайм по тем же кодам их выбирает:

```bash
python tools/export/export_gemm_rtp.py --target whisper-tiny --arch 1 \
    --npu-extra-ops conv,attn,mproj,logit,layn,softm,gelu

./runtime/build/npueembeddings transcribe whisper-tiny audio.wav \
    --npu-extra-ops conv,attn,mproj,logit,layn,softm,gelu
```

Список один и тот же: имя флага общее, и код, который нельзя построить,
отвергается на месте (`parse_exportable` печатает строку в stderr, а не
молча выбрасывает код).

### Что где считается

См. [Где что выполняется](#где-что-выполняется). Две строки там безусловны:
argmax и подавление токенов, и **decode + merge** — это BPE
longest-common-sequence по id. Ни то, ни другое не матрица, поэтому никакой
дизайн их не выражает; это не решение о расписании, которое ещё можно
пересмотреть, а свойство задачи.

### Длинное аудио

Аудио длиннее 30 с режется окнами по 30 с с шагом 5 с **с каждой** стороны, то
есть соседние окна начинаются в 20 с друг от друга, а тексты склеиваются тем же
longest-common-sequence по id, которым пользуется `transformers` без
таймстемпов. Короче 30 с — дополняется нулями, длиннее — режется.

### Опции

| | |
|---|---|
| `--language en` | язык, который **назван**, а не определён: детектора нет, и угаданный язык даёт уверенный перевод не того |
| `--task transcribe\|translate` | задача |
| `--max-new N` | потолок генерируемых токенов на окно; 0 — собственная граница модели |
| `--chunk-seconds N` | длина окна (по умолчанию 30, модельная) |
| `--stride-seconds N` | шаг с каждой стороны (по умолчанию 5) |
| `--convert` | принимать через ffmpeg то, что WAV-читалка не берёт |
| `--json` | JSON-объект в stdout, диагностика в stderr |
| `--npu-extra-ops CODES` | что из семи операций уходит на массив |

### Эндпоинт

`POST /v1/audio/transcriptions` в той же форме, что у OpenAI. Запросы
**последовательные**: декодер держит один KV-кэш и один счётчик, и два
одновременных запроса в одном процессе вмешались бы в ответ друг друга.

### Режим питания NPU

`--bo-mode host_only|host_only_1m|ext|ext_1m` — выбирается **до** создания

## Классификация изображений

Контейнер `google/vit-base-patch16-224` — это **классификатор изображений**, а не
эмбеддер: он отвечает на вопрос «метка для этой картинки», у него нет режима
пулинга, который можно запросить, и он работает через собственный режим.
`npuembeddings list` показывает такую строку как `cls`.

Это тот же самый ViT, который был бы и эмбеддером: картинка 224×224 режется на
196 патчей 16×16 плюс один токен `[CLS]` — итого 197 токенов шириной 768 через
12 слоёв трансформера с pre-LayerNorm. Классификатором его делает последний
шаг: вектор `[CLS]` умножается на хранимую матрицу `[768, 1000]`, и максимум
даёт номер класса. Эта сборка отдаёт **только** это; эмбеддинг из 768 чисел не
экспонирован, и добавить его — правка головы, а не новый набор дизайнов.

1000 классов — это ImageNet-1k и ничего больше. Модель обязана выдать один из
них даже для картинки, которая не принадлежит ни одному, поэтому на входе вне
распределения вы получите уверенную неверную метку, а не отказ. Поэтому любая
цифра точности ниже относится к картинкам из распределения ImageNet.

### Что пользователь скачивает

**Только `model.safetensors`.** В репозитории лежит один маленький файл —
`preprocessor_config.json`, потому что его `image_size`, код ресайза и mean/std
*и есть* фронт-енд: пакер отказывает чекпоинту без него, и больше нигде в
дереве этих чисел нет, так что неверное mean даёт контейнер, который
классифицирует гладко и неверно. 160 байт, одинаково у всех. Геометрия
намеренно **не** коммитится, в отличие от whisper-овского `config.json`: у
геометрии один владелец — сам чекпоинт, который перечитывается на момент
упаковки и закреплён в `CHECKPOINT.json`.

### Четыре команды, и третья — та, которую пропускают

```bash
# 1. контейнер. --max-seq передавать НЕ надо: для этого семейства он
#    отказывается поимённо, потому что число позиций у ViT равно
#    (224/16)^2 + 1 = 197 и задаётся размером картинки, а не вызывающим.
python tools/pack/pack_npue.py --model-dir models/vit-base-patch16-224 \
    --out models/vit-base-patch16-224.npue --device npu1
#    для 90 МБ контейнера (из 175) добавьте --int8

# 2. набор дизайнов под тот контейнер, который вы упаковали.
python tools/export/export_gemm_rtp.py --target vit-base-patch16-224 --arch 1

# 3. ТОЛЬКО если вы паковали --int8: ВТОРОЙ набор дизайнов, экспорт с --int8.
python tools/export/export_gemm_rtp.py --target vit-base-patch16-224 --arch 1 \
    --int8 --out runtime/vit-base-patch16-224-i8
mv runtime/vit-base-patch16-224-i8/vit-base-patch16-224/artifacts_npu1/gemm_rtp \
   runtime/vit-base-patch16-224-i8/gemm_rtp

# 4. классификация.
./runtime/build/npuembeddings classify vit-base-patch16-224 photo.png
```

**int8-контейнеру нужен свой набор дизайнов, и это не мелочь.** У двух
контейнеров *идентичные* формы GEMM, идентичная раскладка и одинаковые
`tile_k 64, tile_n 48, mac_s 8, mac_t 4`; различается только тип операнда,
`I8` против `BF16`. `b_layout_hash` покрывает и тип, поэтому int8-контейнер
просит хеш `8f858f40...`, а bf16 — `52a4adad...`, и один набор обслуживает
ровно один из них. Направить int8-контейнер на bf16-набор — отказ поимённо,
а не молчаливая выгрузка несовпадающих операндов; см. `design_selection.hpp`,
tasks/0080.

`mv` в шаге 3 не косметика. Экспортёр дописывает `<model>/artifacts_npu<arch>` к
тому, что указано в `--out`, и набор оказывается на три уровня вглубь, тогда
как резервный скан рантайма ищет `runtime/*/gemm_rtp/design.json` на два уровня
ниже. bf16-набор из шага 2 находится по имени, поэтому двигать его не нужно.

**`--max-seq` для этого семейства отказывается поимённо.** Отказ, а не тихое
исполнение, потому что исполнять нечего: 197 получается арифметикой по
`image_size` и `patch_size` самого чекпоинта, а не из аргумента, и отказ
называет это число вместо того, чтобы заставлять вас его вычислять. Раньше флаг
принимался и терялся, выходя с кодом 0, — это ровно тот fail-open, который в
этом репозитории считают дефектом. У whisper флаг действительно опасен — таблица
короче одного аудиоокна отказывается и там, аргумент прокинут и проверяется, а не
выбрасывается.

`--arch 1` — это `npu1`. `--arch 2` целится в другую плату (8 колонок AIE) и
не может быть ни собран, ни запущен на машине с одним NPU.

### Где что выполняется

| | на NPU | на хосте |
|---|---|---|
| вклейка патчей | да — едет на потоке `attn_out` | — |
| 12 x qkv / attn_out / ffn | да, 49 диспетчеризаций | — |
| фронт-енд картинки | — | декод, ресайз к 224 как в PIL, `(x/255 - mean)/std`, im2col |
| LayerNorm | — | fp32, с eps из контейнера |
| softmax, GELU | — | внимание O(seq^2) на хосте: 197×197 × 12 голов |
| голова классификатора | — | matvec 768×1000 |

Вклейка патчей бесплатна: её форма `[196, 768] x [768, 768]` **и есть** форма
`attn_out`, поэтому она едет на том же потоке и не стоит ни нового дизайна, ни
нового потока. Голова на хосте потому, что 1000 не делится на
`tile_n * cols`, то есть легальной панели B такой ширины на этом массиве не
существует, а один matvec на хосте дешевле, чем ~150 мкс диспетчеризации.

### Измерено на npu1

RyzenAI-npu1, прошивка 1.5.5.391, XRT 2.26.0. По 25 выборок на контейнер на
5 картинках, вперемежку, прогрев отброшен:

| контейнер | на массиве | медиана | среднее | разброс | диспетчеризаций |
|---|---|---|---|---|---|
| bf16 | 166.8 MB | 0.280 с | 0.2748 с | 0.25–0.30 с | 49 |
| int8 | 85.2 MB | 0.190 с | 0.1864 с | 0.17–0.20 с | 49 |

Распределения не пересекаются (худший int8 0.20 быстрее лучшего bf16 0.25),
значит **для этой модели ширина операнда действительно покупает скорость, а не
только память** — 1.47×, на 32% меньше времени на картинку. Это противоположно
тому, что написано в ветке whisper в `pack_npue.py`, и здесь это измерено, а не
предположено: дизайн фиксирован на M=1024, а у модели 197 строк, поэтому массив
всё равно гоняет полноразмерный дизайн, а i8-операнды вдвое уменьшают объём
переносимых байт. Разделение хост/NPU внутри этих чисел **не измерялось**;
объяснение через M=1024 — повод для правдоподобия, а не измерение.

### Что НЕ измерено

Прочитайте это, прежде чем цитировать таблицу выше как результат.

- **Нет top-1 на данных ImageNet.** Все картинки, прогнанные в этом репозитории
  до сих пор, — иконки PNG, логотип в JPEG или серый квадрат, то есть всё вне
  распределения обучения. Рантайм ни разу не сверялся с `transformers` на
  *диспетчеризуемом* пути, поэтому паритет логитов не заявлен. Транспонированная
  панель или разъехавшийся `im2col` напечатают гладкие, уверенные, полностью
  неверные метки; `verify_vit_model.py` существует именно потому, что это
  отказ, который не объявляет о себе, и он держит хостовую половину.
- **Пропускная способность не прогнозируется.** Та же оговорка, что в разделе
  про распознавание речи: измерений выше seq 64 в этом репозитории нет, а в
  этом контейнере 197 позиций.
- **`npu2` не проверен.** Второй платы не было.

## Сборка наборов дизайнов

### `tools/data/npu_targets.json`

Единый источник геометрии: `seq`, `tile_m`, `tile_k`, `tile_n`,
`identity_threshold`, `hidden`, `intermediate`, `qkv_n`, `layer_norm_eps`,
`vocab`, `heads`, `head_dim`, `frames`, `max_target`. Приоритет: флаг CLI, потом
`model.overrides`, потом `arches[arch]`, потом `defaults`.

`layer_norm_eps` и `vocab` добавлены не для удобства. Epsilon **вкомпилирован**
в ядро (`kernels/layernorm.cc`, `-DLN_EPS`) и стоит **внутри** квадратного
корня, поэтому 1e-5 у whisper и 1e-12 у MiniLM — не разница округления;
`design.json` записывает то, с чем собрано, и рантайм сверяет это с контейнером и
отказывается по имени при расхождении. `vocab` нужен потому, что ширина чанков
проекции в словарь — свойство модели, а не экспортёра.

### Флаги экспортёра, которые стоит знать

| | |
|---|---|
| `--target NAME` | модель из каталога; без него работает исторический ручной путь |
| `--arch 1\|2\|all` | поколение; `all` спавнит по процессу на поколение |
| `--npu-extra-ops CODES` | что строить: `conv,attn,mproj,fft,logit,layn,softm,gelu` |
| `--ln-cols`, `--ln-eps` | ширина строки и epsilon дизайна LayerNorm; по умолчанию из цели |
| `--sm-cols`, `--sm-rows`, `--sm-variant` | геометрия softmax: ширина строки, её ёмкость и ядро |
| `--gelu-variant poly\|erf` | `poly` — фита степени 8 (2.49e-3 от точного erf), `erf` — `kernels/gelu_erf.cc`, активация, которую объявляет контейнер whisper |
| `--identity-threshold N` | сколько различающихся байт в xclbin ещё считается той же статической конфигурацией |

Про `--identity-threshold`: значение по умолчанию поднято с 80 до 128, и это
измеренное решение, а не настроечная ручка. Два xclbin одной формы этого
инструментайна отличаются в шести областях — UUID, заголовке, `aie_image` с
контрольной суммой сборки, поле `"aie_TimeStamp"` и 32-символьном hex UUID — и
число расхождений гуляет между 69 и 82 байтами в зависимости от того, сколько
случайных байтов UUID совпало. 80 был на один байт короче худшего случая, и
набор с корректными формами отказывался экспортироваться. Та же инспекция
говорит, что в другую сторону проверка бессильна: четыре исходных потока
энкодера имеют по-настоящему разные формы и расходятся на те же 69–79 байт,
потому что разница формы — это размер буфера, а не статическая программа.
128 оставляет запас на разброс UUID и всё ещё на три порядка ниже секции
программы.

### Набор дизайнов не переносится между машинами

xclbin привязан к поколению (`npu1` / `npu2`), и `design_fits()` отказывает
набору, построенному для другого. Порядок байтов B-операнда зависит от
поколения: **npu2 (8,8,8), npu1 (4,8,4)**. Все контейнеры были упакованы под
npu2, и npu1-дизайны читали панели с переставленными столбцами. Ничто
структурное этого не замечает: байты те же, формы те же, `layout_hash`
совпадает с обеих сторон (одна и та же неверная константа). Видит только
оракул, и выглядит как числовая ошибка: 1-cos ≈ 0.87 при гейте 2e-3.

### Пересборка идемпотентна, артефакты в gitignore

`*.npue`, `runtime/*/artifacts*` и `runtime/build/` не в репозитории. Шесть
whisper-конфигов на модель **в** репозитории намеренно: это то, что делает
checkout запускаемым после скачивания одних весов.

## Точность

Гейт `worst 1 - cos ≤ 2e-3` по всем строкам, внутри процесса, без Python.

Whisper, измерено на `whisper-tiny` против `transformers`
(`tools/verify/verify_whisper_model.py`, `tools/verify/verify_whisper_features.py`):

| путь | измерено | гейт |
|---|---|---|
| энкодер, всё на хосте | enc 1-cos 1.7e-4 | 2e-3 |
| энкодер, свёртка на массиве | enc 1-cos 1.4e-4 | 2e-3 |
| энкодер, LayerNorm на массиве | enc 1-cos 1.7e-4 | 2e-3 |
| энкодер, GELU на массиве | enc 1-cos 1.6e-4 | 2e-3 |
| энкодер, attention на массиве | enc 1-cos 2.2e-4 | 2e-3 |
| фронтенд, банк mel на массиве | mel max\|d\| 9.4e-4, conv 1.9e-3 | 1e-3 / 2e-2 |
| фронтенд, трансформация на массиве | mel max\|d\| **0.307** | 0.5 (свой) |
| GELU, ядро против `std::erf` | max\|d\| 4.05e-3 | 1 ULP bf16 |

Строка трансформации — единственная, где массив **не эквивалентен** хосту, и
это записано в допуске гейта, а не спрятано: 0.307 против 3e-5, потому что
прямой DFT против bf16-вилок имеет шумовой пол. Громкие бины сходятся до 0.2%.

Что этот гейт есть и чего нет: `1 - cos` — проверка арифметики, а не качества.
На int8-контейнере `bge-large-en-v1.5` измерял 2.968e-03 против гейта 2e-3,
проходя MTEB на среднем −0.05. Качество приходит из MTEB; этот гейт — сигнал
регрессии.

## Известные дефекты

- **Объявлено в контейнере `not_implemented`:** beam и sampling (только
  greedy), определение языка (язык называется, умолчание печатается как
  `ASSUMED`), таймстемпы (значит, merge по времени невозможен; перекрытие при
  этом обработано LCS-слиянием).
- **Перекрытие CPU/NPU не сделано:** энкодер и декодер ждут друг друга.
  Пункт про скорость, отложен по решению владельца.
- **Турбо (32 слоя) расходится с transformers сильнее допуска этого гейта:**
  enc 1-cos 3-6e-3 против 2e-3, и столько же с хостовой свёрткой. Расхождение
  реальное и расширением допуска не лечится; вопрос в том, 32 ли это слоя или
  геометрия designs.
- **Параллельный перенос CPU/NPU для эмбеддеров сделан, для whisper — нет.**

## Замечания по производительности

**Сначала измеряйте, потом верьте цифре, и измеряйте на своей машине.** Ниже
механизмы, которые на самом деле решают число.

- **Массив делится.** Wall clock сам по себе не есть утверждение о
  производительности NPU: замер 221 seq/s против истинных 694 на том же бинаре
  через минуты, из-за оставшегося процесса с активным `hw_context`.
  `xrt-smi examine -r all` знает, кто что держит; рантайм отказывается от
  замера на неэксклюзивном массиве, если не передать `--allow-contention`.
- **Стоимость диспатча фиксирована и не мала** (~150 мкс измерено). Набор
  дизайнов грузится один раз и держится именно ради этого — и поэтому
  элементарные операции по умолчанию на хосте, и поэтому `--npu-extra-ops`
  может **снизить** пропускную способность, а не поднять.
- **Слои контекстов подобраны, а не подложены.** Запрос режется на наибольший
  подходящий тир; у набора свой поток инструкций на тир.
- **`--npu-extra-ops` стоит `hw_context` на именованную операцию.** Шесть на
  npu1, whisper занимает два. XRT не даёт запроса на количество, поэтому бюджет —
  помеченная константа, а источник числа печатается рядом, а не зашивается
  молча.
- **Синтез списка вилок против `aie::tanh` стоил 1%.** GELU пришлось считать
  полиномом (`kernels/gelu_poly.cc`), пока для whisper не появился
  `kernels/gelu_erf.cc` — потому что контейнер объявляет `activation: gelu`, и
  тангенс-полином это другая функция, а не более быстрая та же.

| `runtime/include/whisper/`, `runtime/src/whisper/` | стек Whisper: фронтенд, энкодер, декодер, транскрипция, и пять новых файлов на операции: `eltwise`, `attention_npu`, `mel_proj`, `fft_npu`, `logits_npu` |
| `runtime/tests/` | стенды гейтов |

Новые файлы операций, которые читаются первыми при разборе:
`attention_npu.hpp` (почему attention упирается в панели, а не в диспатчи),
`logits_npu.hpp` (почему словарь нарезан на чанки и почему это всё равно не
выгодно), `fft_npu.hpp` (что стоит прямой DFT против fp64 и почему он не
эквивалентен).
