# 0063 — EmbeddingGemma-300M: C3 host kernels (RMSNorm, RoPE, GeGLU), verified against real intermediates

- **Date** 2026-08-20
- **Milestone** M12 (research plan Del C, first slice of C3)
- **Status** done, scoped exactly as asked: three standalone kernels, not wired in

## Goal

Build the first slice of C3 (the `arch=1` runtime branch) from
`tasks/0061-m12-embeddinggemma-tokenizer/TASK.md`'s "Next" section and the
user's go-ahead ("Vi kjører Gemma", T29 in `research/OPEN-THREADS.md`): three
standalone C++ host kernels EmbeddingGemma's layer sandwich needs that
MiniLM/BERT never did — RMSNorm (incl. the per-head `q_norm`/`k_norm`
variant), RoPE application to Q/K with per-layer base-frequency selection,
and the GeGLU elementwise stage (`gelu_pytorch_tanh(gate) * up`) — each
independently verified against `reference/encoder_gemma.py`'s numpy
implementation on real intermediate values from the real checkpoint.
**Explicitly out of scope, not attempted**: wiring into `main.cpp`'s
`Encoder::run()` (the `arch=1` branch), `hub.cpp`'s model catalogue, or any
`.npue`/packer change. No NPU, no IRON, no Peano — pure host fp32 C++,
matching `tasks/0061`'s own scoping discipline exactly.

## Context

- `reference/encoder_gemma.py` (tasks/0055) is the ground-truth numpy oracle,
  matching HuggingFace to `1-cos` 1.065e-07. It documents two easy-to-miss
  facts this task had to get exactly right: RMSNorm is `x/rms(x)*(1+w)`, NOT
  the more common `x/rms(x)*w`; and RoPE's base frequency (theta) is
  **per layer** — layers 5, 11, 17, 23 (0-indexed, `(i+1) % 6 == 0`) use
  `rope_theta` (1e6, "full_attention"), every other layer uses
  `rope_local_base_freq` (1e4, "sliding_attention").
- `reference/goldens_gemma/embeddinggemma-300m_l24_s64_taps.safetensors`
  (gitignored, regenerated by `reference/make_goldens_gemma.py --taps` in
  tasks/0055) already holds a full intermediate dump — every named
  `tap()` call in `GemmaEmbeddingReference.encode()` — from one real forward
  pass of the real `unsloth/embeddinggemma-300m` checkpoint over 4 real
  sentences (the "document"-prefixed corpus, batch 4, seq_len 64, 560
  tensors). This task reads directly from that file rather than re-running
  the model, so no torch/HuggingFace call happens in this task at all.
- `runtime/src/main.cpp`'s `layer_norm_cpu` (~line 781) and `gelu_cpu`
  (~line 930) are the existing BERT host-eltwise kernels this task matches
  in style (plain C++ / AVX2 intrinsics on `float*` buffers, no external math
  library) without modifying either — Gemma needs different formulas
  (RMSNorm not LayerNorm, tanh-GELU not erf-GELU) so these are new,
  additional functions.
- `runtime/src/tokenizer_gemma.cpp`/`.hpp` + `tokenizer_gemma_cli.cpp`
  (tasks/0061) are the direct precedent for "standalone kernel, verified in
  isolation, built by hand with `cl.exe`, not touching `runtime/CMakeLists.txt`
  or the shared `runtime/build/` directory" — this task follows that pattern
  exactly.

## What was built

1. **`runtime/include/gemma_kernels.hpp` + `runtime/src/gemma_kernels.cpp`**
   (127 + 200 lines) — the three kernels:
   - `rms_norm_cpu(x, weight, out, rows, dim, eps)` — `x/rms(x)*(1+w)`,
     reduction over the last `dim` elements of each of `rows` contiguous
     vectors. **One function serves both RMSNorm uses** in the model: the
     four per-layer full-hidden norms (`dim=768`) and the per-head
     `q_norm`/`k_norm` (`dim=256`) — same formula, same reduction axis, only
     which axis is contiguous in memory differs, and that is the caller's
     layout choice. Reduction (sum of squares) and the final multiply are
     both done in **double precision**, matching
     `reference/encoder_gemma.py`'s `rms_norm()` exactly (it upcasts to
     float64 explicitly) — not a speed/accuracy trade, a precision-matching
     one, without which byte-for-byte agreement would be structurally
     impossible. AVX2: the double-precision reduction and the final multiply
     are both vectorized 4-wide (`__m256d`) — same precision, parallel lanes,
     not a precision trade.
   - `gemma_is_full_attention_layer(layer_idx, sliding_window_pattern=6)` —
     `(layer_idx+1) % pattern == 0`, the per-layer theta selector.
   - `gemma_rope_tables(seq_len, head_dim, base, cos_out, sin_out)` —
     `inv_freq[j]=base^(-2j/head_dim)`, `freqs[s,j]=s*inv_freq[j]`,
     `emb=concat(freqs,freqs)` (rotate-half convention, not interleaved).
     Computed in double precision, rounded to float32 only at the end —
     matches `rope_cos_sin()` exactly.
   - `apply_rope_cpu(x, cos, sin, out, rows, seq_len, head_dim)` — applies
     the rotation to `rows` contiguous head_dim vectors, position recovered
     as `row % seq_len` (matches the `[B,H,S,D]` row-major layout the taps
     use). Computed in **float32** throughout, matching the reference's
     `apply_rope()` exactly (it does NOT upcast to float64 — plain float32
     numpy arithmetic). AVX2 8-wide float32. In-place safe (internal
     per-row scratch copy — `out[j]` reads both halves of `x`'s row).
   - `geglu_cpu(gate, up, out, n)` — `gelu_pytorch_tanh(gate) * up`, NOT
     `main.cpp`'s exact-erf `gelu_cpu` (untouched, separate function).
     Deliberately left **scalar**: the double-precision formula calls
     `std::tanh()` per element (no AVX2 intrinsic exists for it), and
     matching the reference's exact **two-stage rounding** — `gelu_tanh()`
     itself rounds to float32 before the caller multiplies by `up` (also
     promoted back to float64 for that multiply, rounded again) — mattered
     more than vectorizing the cheap arithmetic around an unavoidable scalar
     transcendental call. This one instruction: `const float act =
     static_cast<float>(0.5*x*(1.0+t));` (rounds), then
     `static_cast<double>(act) * static_cast<double>(up[i])` (promotes the
     *rounded* value back up) is what makes this bit-exact against the
     reference below — collapsing it into one float64 expression would not
     have been.
2. **`tools/dump_gemma_kernel_vectors.py`** (194 lines) — build-time-only
   Python (CLAUDE.md rule 5), reads the existing taps safetensors file plus
   `config.json` and `model.safetensors` (for the norm weights, which are
   not in the taps file), and writes a flat binary (`GKK1` magic, 36
   records) of `(name, kind, before, after)` triples the C++ harness reads
   with `ifstream`. **Every "before"/"after" pair is a REAL value from the
   one real forward pass** — the tensor immediately upstream of a given op
   and the tapped tensor immediately downstream of it — not a value
   recomputed a second time by calling the reference function again (except
   where reshape/transpose is needed to align row order between the taps'
   `[B,S,H*D]` pre-reshape and `[B,H,S,D]` post-reshape tensors for the
   per-head RMSNorm case, which is a pure axis permutation, not a value
   change). Covers 4 layers (0, 5, 11, 23 — spanning both RoPE branches and
   both attention-head counts) × the relevant sites per kernel.
3. **`runtime/src/gemma_kernels_test.cpp`** (≈220 lines) — standalone CLI,
   same role as `tokenizer_gemma_cli.cpp`: reads the vector file, runs the
   matching kernel on each "before" block, and reports `rel_fro`, `max_abs`,
   `mean_abs`, `max_rel` per record against the tapped "after" block, plus a
   pure unit check of `gemma_is_full_attention_layer` against the known
   `{5,11,17,23}` set. **Gates on `rel_fro` (this project's own standard
   per-tensor accuracy metric), not `max_abs`** — EmbeddingGemma's deep-layer
   activations range from O(1) to O(1e4) (L23's `ln_post_ffn` reaches
   `|x|≈28,357`), so a fixed absolute-diff threshold is either meaninglessly
   loose on small tensors or falsely fails on large ones from float32 ULP
   scaling alone — which is exactly what happened during development (see
   Problems hit). Exits nonzero if any record's `rel_fro` exceeds the
   tolerance (default `1e-5`).

## Result

**36/36 records PASS** (rel_fro gate, tolerance 1e-5) — full output in
`verify_gemma_kernels.txt` (this folder). Summary by kernel, `rel_fro`
across all layers tested (0, 5, 11, 23):

| kernel | records | rel_fro range | notes |
|---|---:|---|---|
| RMSNorm, full hidden (dim=768) | 16 | **0.0 (bit-exact)** to 2.75e-11 | 12 of 16 sites are bit-exact; the four non-zero ones (all `ln_post_ffn`, the largest-magnitude activations) top out at rel_fro 2.75e-11, `max_rel` ≤1.19e-07 — exactly one float32 ULP |
| RMSNorm, per-head (dim=256, `q_norm`/`k_norm`) | 8 | **0.0 (bit-exact)**, all 8 | every case bit-identical to the tapped `q_normed`/`k_normed` |
| RoPE (`apply_rope_cpu` + `gemma_rope_tables`) | 8 | 1.74e-08 to 4.26e-08 | `max_abs` 9.537e-07 to 1.907e-06 (1-2 float32 ULP at this magnitude) on every case; `max_rel` spikes to 4.9e-03 only at RoPE's cos/sin zero-crossings (a property of relative error near zero, not a formula error — `max_abs` stays at the same ULP floor there too) |
| GeGLU (`geglu_cpu`) | 4 | **0.0 (bit-exact), all 4** | the two-stage-rounding fix (see above) was necessary for this: an earlier single-expression version (not committed) measured `rel_fro` ~1e-8, still tiny but not bit-exact |
| `gemma_is_full_attention_layer` | 1 (24 sub-checks) | exact | reproduces `{5,11,17,23}` for `sliding_window_pattern=6` over all 24 layers |

**Every float32 discrepancy found is at or within a couple of ULP of float32
machine epsilon (1.19e-07 relative)** — the RMSNorm/GeGLU non-zero cases are
attributable to AVX2's FMA fusing multiply-add differently than the
scalar/numpy path in a couple of lanes, and RoPE's ~1e-6 absolute floor is
from `std::cos`/`std::sin` (MSVC CRT) vs `np.cos`/`np.sin` (numpy's libm)
differing by roughly one ULP in double precision before both round to
float32. None of this is a formula error. As a negative control (not committed code —
a throwaway numpy check against the same real tapped tensors), the three
documented gotchas were deliberately reintroduced and measured against the
same real "after" tensors used above:

| deliberate mistake | rel_fro | vs. this task's actual result |
|---|---:|---|
| RMSNorm without the `1+` (`x/rms*w`, Llama-style) | **0.439** | 0.0 (bit-exact) |
| RoPE with the wrong per-layer theta (1e4 on layer 5, which needs 1e6) | **0.757** | 0.0 (bit-exact) |
| GeGLU with exact-erf GELU (`main.cpp`'s BERT formula) instead of `gelu_pytorch_tanh` | **3.255e-04** | 0.0 (bit-exact) |

Three to six orders of magnitude larger than anything measured on the actual
implementation, confirming these are the failure modes the design comments
in `gemma_kernels.hpp` warn about, and that this task's numbers are not
accidentally passing a weak test.

## Problems hit

- **The test harness's own tolerance was wrong on the first run, not the
  kernel.** Gating on a fixed `max_abs < 1e-4` failed exactly one of 36
  records (`rmsnorm_full_L23_ln_post_ffn`, `max_abs=9.766e-04`) — investigated
  by checking the tapped tensor's own magnitude (`np.abs(a).max()` = 28,357.0)
  and finding `max_rel` was already 1.19e-07 (float32 epsilon) even on the
  "failing" case. A fixed absolute threshold cannot be right across tensors
  spanning four orders of magnitude in this model; switched the gate to
  `rel_fro` (this project's own standard per-tensor metric elsewhere in
  `tasks/`), which is scale-aware by construction. Left `max_abs`/`mean_abs`/
  `max_rel` in the report for diagnostics, with a comment explaining why
  `max_rel` alone is also misleading (it spikes near RoPE's zero-crossings
  for a reason unrelated to correctness).
- **GeGLU needed the reference's exact two-stage rounding, not just its
  formula.** An intermediate version computed
  `0.5*x*(1+tanh(...))*up` as one double-precision expression (mathematically
  identical to the reference's formula) and measured `rel_fro` ~1e-8 against
  the tapped `L*.geglu` values — already far inside any reasonable tolerance,
  but not the bit-exact 0.0 the final version gets. Reading
  `reference/encoder_gemma.py`'s `gelu_tanh()`/`mlp()` again showed why:
  `gelu_tanh()` returns a **float32-rounded** value (`act`), and `mlp()`
  promotes that already-rounded `act` back to float64 before multiplying by
  `up` — an extra rounding step a single fused expression skips. Matching it
  (round to `float act` mid-computation, then re-promote) closed the gap to
  exactly 0.0 across all four layers tested.
- **The per-head RMSNorm "before" tensor needed a transpose that does not
  change any value**, only row order — `q_proj`/`k_proj` taps are
  `[B,S,H*D]` (pre-reshape), `q_normed`/`k_normed` taps are `[B,H,S,D]`
  (post-reshape-and-transpose). Reshaping `q_proj` to `[B,S,H,D]` and
  `.transpose(0,2,1,3)`-ing it in the dump script (a pure numpy view
  permutation) aligns both sides on the same `(b,h,s)` row order without
  needing a second reference-function call — confirmed by the resulting
  comparison being bit-exact (0.0 `rel_fro`), which would not be possible if
  the transpose had silently reordered which values paired with which.
- No blockers otherwise. `.venv-ref`, the pinned checkpoint, the existing
  gitignored taps file, and `cl.exe` via `vcvars64.bat` were all already in
  place from tasks/0055/0061; nothing needed installing or regenerating.
  `ironenv`/the NPU were never touched, as scoped.
