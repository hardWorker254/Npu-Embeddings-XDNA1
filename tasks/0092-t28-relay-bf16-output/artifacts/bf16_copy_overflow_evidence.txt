    func.call @ffn_down_hop_matmul_g2_64x48x16(%1, %w_hop0, %ffn_down_acc)

        : (memref<6144xbf16>, memref<1536xbf16>, memref<1024xbf16>) -> ()

   actually allocates and what the compiler's own memory map assigns it

   ffn_down_acc is allocated exactly 2048 B (bf16 x 1024), matching its MLIR

3. llvm-objdump -d on the cached ffn_down_hop_matmul_g2_64x48x16.o (the
   symbol actually linked in, compiled straight from
   experiments/m5-eltwise/kernels/ffn_down_hop_matmul_g2.cc's
   `float *restrict acc` signature, REGARDLESS of what arg_types the Python
   side declares -- confirmed by reading kernel.py's `external_func(...,
   inputs=self._arg_types)`, which only shapes the MLIR func.call
   declaration, never the linked object). Store pattern at the end of the
   m-loop, storing the accumulator row back to `acc`:

    31a: vst  bmll3, [p5], #0x40    ; write, then advance p5 by 0x40 (64 B)
    31e: vst  bmll1, [p5, #0x0]
    322: vst  bmll0, [p5, #0x40]
    (four "bm*" quarters stored per row elsewhere in the loop body --
    bmll/bmlh/bmhl/bmhh together = a full 512-bit / 64-byte vector store,
    i.e. 16 x fp32 = 64 B per row)

   64 rows x 64 B/row = 4096 B written through `acc`, against the 2048 B the
   BF16_COPY-declared Buffer actually allocates. This is llvm-objdump-level
   confirmation of the type mismatch tasks/0092's brief asked to check for.

CONCLUSION (see TASK.md for the full writeup): this mismatch is real and
objdump-confirmed, but a controlled re-test with a genuinely bf16-accumulator
twin kernel (`ffn_down_hop_matmul_g2_64x48x16_bf16acc`, added this session,
zero overflow, verified via the same input_with_addresses.mlir technique to
be consistently bf16-typed end to end) hangs IDENTICALLY. So the overflow is
a real, independent bug in the discriminator -- now fixed -- but it was NOT
the cause of the hang. The hang is real and survives the fix.
