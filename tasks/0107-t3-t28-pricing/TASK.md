- **Milestone** M13 (T3, T28)

1.44× "array-infinite" ceiling — then recommend build / price-further / park.

### 1. Which datapath the estimate is for

**The bfp16-emulated MMAC + bf16-C datapath** (`--emulate-bfp16 --c-bf16`),

`bge-small-en-v1.5` stays on plain bf16 — MTEB fail). This is the datapath
that ships for most of the catalogue as of 2026-08-24, and per the brief it
is the one whose direction matters: bfp16 is faster on the array than plain
bf16, which shrinks the array's share of the encode and therefore shrinks
what any transport-removing lever (T3/T28's mechanism) can win.

**Neither of the two granular breakdowns this project has on file is for
this datapath.** [note 0007](../../research/notes/0007-unused-iron-surface.md)'s

### 2. What T28's built mechanism actually removes

The relay (0062/0092) fuses exactly the `ffn_up → GELU → ffn_down` chain: GELU
runs **on the array**, at each producer core, before the merge join, and the
intermediate never crosses to host. So the candidate host-side costs it
removes are: **all of `host gelu`** (GELU only ever runs after `ffn_up`, so
this line is 100% attributable), plus **the portion of the transport bucket**
(`bf16 convert` + `sync to device` + `sync from device` + `read out + bias`)
that belongs to `ffn_up`'s C-readback and `ffn_down`'s A-upload specifically —
not qkv's or attn_out's.

**Allocating the transport bucket by shape.** Transport scales with tensor
size, which for a fixed M (=8192, batch×seq) scales with each shape's N (bf16,
2 bytes/elem — C traffic ∝ N; A/weight traffic tracks similarly for these
tile geometries). For every BERT-family (arch=0) model in this catalogue, the
four shapes are qkv (N=3h), attn_out (N=h), ffn_up (N=4h), ffn_down (N=h,
K=4h) — a ratio that is **architecture-invariant** (h cancels):

```
qkv : attn_out : ffn_up : ffn_down  =  3h : h : 4h : h  =  3 : 1 : 4 : 1   (sum 9)
ffn_up share = 4/9 = 44.4%      ffn_down share = 1/9 = 11.1%
ffn_up + ffn_down = 5/9 = 55.5%
```

This is an **assumption** — it treats the transport bucket as splitting by
N-proportional bytes moved, uniformly across `bf16 convert`, `sync to/from
device`, and `read out+bias`, which is a first-order approximation, not a
per-shape measurement (no per-shape transport breakdown exists; `--bench`
reports the bucket only at the whole-encode level). If the true split is more
concentrated on `ffn_up` (plausible — it is the single widest N in the model)
the estimate below is a **lower bound** on the addressable fraction; if it is
less concentrated, an upper bound. Flagged, not resolved.

### 3. The arithmetic

```
addressable_ms  =  0.555 × (bf16_convert + sync_to + sync_from + read_out_bias)  +  host_gelu
best_case_wall  =  wall − addressable_ms                         (zero rebuild overhead assumed)
best_case_speedup = wall / best_case_wall
```

| model | transport bucket | addressable (0.555×transport + gelu) | % of wall | best-case speedup |
|---|---:|---:|---:|---:|
| MiniLM | 52.85 ms | 29.33 + 6.70 = **36.03 ms** | **25.9%** | **1.35×** |
| bge-base | 198.22 ms | 110.01 + 38.05 = **148.06 ms** | **23.9%** | **1.31×** |
| bge-large | 528.35 ms | 293.24 + 106.65 = **399.89 ms** | **19.7%** | **1.25×** |

**These three cluster at 1.25×–1.35×, and the ordering is the one this project's
traffic model always predicts: the smaller/more host-bound model (MiniLM) has
more to win than the array-bound one (bge-large).**

**This is a best case, not a prediction.** It assumes: (a) zero added latency
from the extra mem-tile hops the relay introduces — unmeasured, because no
trace exists for this design (trap 7; T28 item (c), unchanged by this task);
(b) the relay's second-stage matmul is as fast as `kernels.mm()`'s
MMAC-accelerated GEMM — it is not: it is hand-written, and
[`0091`](../0091-t7-t8-gelu-poly/TASK.md) measured that specific inner loop
carrying T7's emulated-widen idiom, i.e. **known inefficient**, and whether it
can be replaced is T28 item (a), still unexplored (§4 below); (c) it applies
uniformly at production scale (GROUP=8, K=1536) — built and correct only at
GROUP=2, K_total=192 (0092). Every one of these pushes the real number *below*
1.25×–1.35×, not above it — this is a ceiling on the ceiling.

### 4. Comparison against the 1.44× figure

**The 1.44× figure is not the right ceiling to compare against, and the
brief's own framing anticipates this.** It is [`0081`](../0081-m13-int8-everywhere/TASK.md)
§3's "if the array were made infinitely fast" bound, on the **int8** datapath —
a different, unrelated lever (raw MAC throughput) from what T3/T28 targets
(host↔device transport of an intermediate). Computing the *analogous*
array-infinite bound on the datapath this estimate is actually for
(`wall / (wall − dispatch_and_wait)`):

| model | dispatch+wait share | analogous array-infinite ceiling |
|---|---:|---:|
| MiniLM | 26.7% | 1.36× |
| bge-base | 36.2% | 1.57× |
| bge-large | 46.4% | 1.87× |

**These are all bigger than int8's 1.44×, not smaller** — bfp16-emulated MACs
are much slower than native int8 MACs (CLAUDE.md: int8 is 5.5–7.7× the bf16
datapath), so on the *adopted* datapath the array is a **larger** fraction of
the encode than on int8, and there is correspondingly more (hypothetical) room
if it were infinitely fast. This is a different comparison from the brief's
"bfp16 shrinks the array's share" claim, which is about bfp16 **vs. plain
bf16** (the pre-adoption datapath), not bfp16 vs. int8 — and that comparison
does check out: `docs/CURRENT_STATUS.md` records bge-base's array share at
**74.1%** of wall clock on the pre-adoption datapath (dated to the 0042/0051
era, batch/config not confirmed identical to 0105's, so read as directional,
not exact) against **36.2%** now. Roughly halved. **The ceiling did move, and
in the direction the brief said it would — just not against the number
(1.44×) the brief asked to check it against, which is a different lever on a
different datapath.**

**What actually bounds T3/T28's specific lever, on the shipped datapath, is
the 1.25×–1.35× computed in §3** — an order of magnitude smaller than T3's
original ~33%-of-encode estimate (note 0007 Part 4), because two things
already happened since that estimate was written, independently of building
any relay: `--emulate-bfp16` sped up the array itself (shrinking the whole
NPU-path bucket, transport included, as a fraction of a now-larger-relatively
host side — except transport bytes did *not* shrink, only their share did, as
the array got faster around them) and `--c-bf16` halved C's bytes at the
source (0104), which is exactly the kind of byte-lever note 0007 flagged as
"a cheaper, independent version" of the same prize. **Much of T3's original
prize has already been collected without building the relay at all.**

## What this does not cover

- **Only arch=0 (BERT) models.** The relay as built handles plain GELU only.
  `nomic-embed-text-v1.5` (gated SwiGLU, arch=2) and `embeddinggemma-300m`
  (gated GeGLU, arch=1) have a different chain shape (`ffn_up` emits `2×
  intermediate`, narrowing in place) and neither the built relay nor this
  estimate's N-share arithmetic (which assumes plain GELU's `4h` ffn_up width)
  applies to them without rework. Not estimated.
- **A precise per-shape transport breakdown does not exist.** §2's 55.5%
  N-share allocation is the best available substitute, stated as an
  assumption per the brief's discipline rule, not measured directly. Building
  one would need per-shape instrumentation `--bench` does not currently emit
  (it reports `read out + bias`/`bf16 convert`/sync lines once, summed over
  all four shapes' dispatches, not broken out per `gemm_rtp` call site).
- **No hardware trace exists for the relay at any scale** (trap 7; T28 item
  (c), still true after this task). Nothing here is a performance
  measurement of the relay itself — it is an estimate of the *prize*, built
  from measurements of the *current, relay-less* pipeline. The brief was
  explicit that this is legitimate as long as it is labelled as such.

## 3. What the third hierarchy tier would cost — and a discrepancy found while pricing it

**L1 budget.** [`0083`](../0083-m13-join-port-budget/TASK.md) already re-priced
this at production geometry, streaming (not one-shot): `(k, N_DOWN) = (64, 48)`
uses **47,104 B of 64,512 — 27% spare**. The 49,152 B one-shot-gather wall
0062/0057 hit does not apply to a real `ffn_down` consumer, which streams
k-blocks like every other GEMM core in this codebase already does. This part
is priced, not open.

**Port budget, and a discrepancy worth flagging.** [`0057`](../0057-m10-t28-cross-column-regather/TASK.md)
and [`0083`](../0083-m13-join-port-budget/TASK.md) together establish that an
**8-source regather fits in TWO tiers**, not three: `8 → 4+4 → 1` (a spare port
each) or `8 → 5+3 → 1` (bit-exact to `N=5`, `N=6` fails). This is a full
8-column production regather, expressed and port-budgeted, in two hops — which
is exactly what a relay core's 2-input-channel ceiling (trap 3b) requires: two
mem-tile sources, read via the relay's own two channels.

**But T28's own "What T28 still needs" list, written by 0092 (2026-08-23, the
most recent update), still says: *"(b′) scaling past this probe's `GROUP=2`...
needs a third hierarchy tier or a different relay strategy. Not designed."***
That sentence sits **below** the 0083 correction block in the same file, which
was appended earlier the same day and states the opposite conclusion (2 tiers
suffice). Reading both in file order: 0083's finding answers "is a third tier
structurally required for an 8-way regather" with **no**, and 0092's list
appears not to have been reconciled with it — the most likely reading is that
"third tier" in 0092's list is loose language for "the second, unbuilt half of
the ALREADY-priced 2-tier design" (going from GROUP=2 built to GROUP=4+4 or
5+3 built), not a literal third hop. This is exactly the shape of failure
rule 3 exists to catch (a register entry not cross-checking a nearby, dated,
un-superseded correction), so it is called out here rather than either
silently trusted or silently overridden. **Recommend the register's T28 item
(b′) be reworded to remove "third hierarchy tier"** unless a future session
finds a concrete reason 2 tiers do not suffice at full production K=1536 (as
opposed to the 512-float synthetic tiles 0083 tested at) — the streaming
arithmetic above suggests they should, but nobody has built and measured the
4+4 or 5+3 case with real compute at N_DOWN=48 across the full K.

**So the real remaining build is not a third tier**, on present evidence — it
is: (1) extending the already-priced 2-tier topology from 2-of-8 columns
(built) to 8-of-8 (priced, not built), at production `N_DOWN=48` and the full
`K=1536` reduction (24 k-blocks of 64, not 0092's 3); (2) whatever real,
un-modeled overhead that adds (extra join fan-in per merge tile, more k-block
iterations through the relay's hand-written matmul); (3) T28 item (a) —
**whether `kernels.mm()`'s MMAC operand order composes with a join's own
`dims_to_stream`.** This remains completely unexplored — no session has
attempted it — and it is not a minor detail: the relay's second-stage matmul
is currently hand-written specifically *because* this is unknown, and
[`0091`](../0091-t7-t8-gelu-poly/TASK.md) independently measured that
hand-written kernel's inner loop as carrying T7's emulated-widen idiom, i.e.
**known slow**, not merely unaccelerated. Until (a) is answered, every number
in §3 above is an upper bound computed against a matmul substantially slower
than the array's normal GEMM path — the true relay, if built with the current
hand-written kernel, would land below even the 1.25×–1.35× best case.
**Extra hops of latency**: unpriced, because no trace exists (item (c)) —
this is the one piece of question 3 that genuinely cannot be answered without
a measurement this task was told not to take.

## 4. Is it worth it — recommendation: park

**Park the third-tier / full-production build. Do not price it further as a
next step; instead port [`0082`](../0082-m13-fused-ffn-epilogue/TASK.md)'s
host-side epilogue fusion to the bfp16/bfp16-emulated datapath first.**

The single strongest reason: **0082 already bought most of the same class of
prize T28 targets — 1.39×–1.48× on int8 — with a pure C++ rewrite, no AIE
routing, no hang debugging, no open MMAC-composition question, in one task.**
It is explicitly **not wired for the datapath five of six models actually
ship on** ("bf16 path untouched," 0082 §5). Trying that first is strictly
cheaper and lower-risk than finishing T28's production build, and it would
also **retire this task's own biggest uncertainty**: after it exists, the
transport bucket in §1's table shrinks the way it did for int8, and the
1.25×–1.35× ceiling computed in §3 (which assumes today's *unfused* host
chain still runs) would need to be recomputed against a smaller remaining
prize — exactly 0007's own point about §6b's estimate ("a cheaper,
independent version... most of the... convert disappears with it"), now
applying to a second, cheaper lever ahead of the hardware one.

**Numbers that drove this, restated:**
- Best case for T28 at full production scale, zero rebuild overhead, arch=0
  models only: **1.25×–1.35×**, and every unresolved item (T28 (a), (b′)'s
  real remaining scope, and (c)'s unmeasured hop latency) can only push that
  number down.
- That is **smaller than the 1.39×–1.48× 0082 already measured on hardware**
  for a comparable mechanism (removing multi-pass host transport around a
  chained GEMM pair), at a fraction of the engineering cost and with none of
  T28's open questions.
- Two sessions ([`0087`](../0087-m13-relay-production-width/TASK.md),
  [`0092`](../0092-t28-relay-bf16-output/TASK.md)) were spent finding and
  fixing **one hang bug** in the 2-column probe, and the root cause both
  times was a plain host-side type/config error, not a hardware limit — this
  is evidence the remaining build (scaling to 8 columns, streaming full K,
  and resolving the MMAC-composition question) carries real, not
  hypothetical, engineering risk on top of an already-modest ceiling.

**This is the same shape of arithmetic that retired T2, T9 and T12**
([`research/CLOSED-THREADS.md`](../../research/CLOSED-THREADS.md)): a real,
correctly-built mechanism whose measured or estimated prize turned out
smaller than a cheaper alternative already on the table. **Not a claim that
T28 is wrong or that the relay work was wasted** — the mechanism is proven
correct on hardware at production tile width (0092), which is real, durable
progress, and the two-tier port topology is real, priced infrastructure for
whoever revisits this. The claim is narrower: **build the cheap thing
first, and re-price the hardware relay once it exists**, rather than
building the more expensive, higher-risk piece against a stale, larger
estimate of what it would save.

## Result

Estimated end-to-end saving from the fully-built T3/T28 relay, on the
bfp16-emulated + bf16-C datapath (the one that ships for 5 of 6 models):
**1.25×–1.35× best case (arch=0 models only), zero rebuild overhead assumed**
— an order of magnitude smaller than T3's original ~33%-of-encode estimate,
because the bf16-C narrowing and the bfp16-emulation speed-up already
happened independently of building the relay. This is **smaller** than the
1.39×–1.48× [`0082`](../0082-m13-fused-ffn-epilogue/TASK.md) already measured
on hardware for a comparable, much cheaper host-side fusion — on int8, not
yet on bfp16. **Recommendation: park the third-tier/full-production relay
build; port 0082's fusion to bfp16 first, then re-price.**

Also found: a likely-stale "third hierarchy tier" claim in T28's own register
entry, contradicted by a same-day, un-reconciled correction lower in the same
file (§3 above) — flagged for the register update rather than silently fixed,
since fixing it requires a call this task is not positioned to make alone.

## Problems hit

1. **The two existing "dispatch share" numbers (0007's 33%, 0081's 30.4%) are
   each for a different datapath than the one that ships**, and neither
   substitutes for the other. Worked around by reading 0105's own raw
   `--bench` logs, which turned out to already carry the needed breakdown
   (host gelu, transport buckets) for the *adopted* datapath — it had just
   never been read past the headline `wait (hardware)` line the register and
   `docs/CURRENT_STATUS.md` quote. No new measurement was needed, only a
   closer read of an existing artifact — worth naming since it is the kind of
   thing rule 3/`tools/check_register.py` exists to prevent happening twice.
2. **No per-shape transport breakdown exists**, only a per-encode total
   across all four GEMM shapes. Allocated by an N-proportional assumption
   (§2), stated explicitly as an assumption rather than presented as
   measured.
3. **A discrepancy inside T28's own register entry** (the "third tier" claim
   vs. 0083's two-tier finding, both present, un-reconciled, in the same
   file) — found while trying to cost the third tier, not by looking for
   register bugs. Recorded in §3 above rather than resolved unilaterally,
   since resolving it requires either a build (to test 4+4/5+3 at production
   K) or a judgement call about which existing measurement 0092's list simply
   failed to incorporate.
